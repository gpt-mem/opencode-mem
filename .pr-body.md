### What does this PR do?

Step 2 of #202: the provider-visible projection of tool output (the compact
marker) did not exist on the v2 line at all — `grep -rn "MemoryContext"
packages/` on `main` matched nothing, so the v2 model context carried every
bounded tool result in full and there was nothing to compress.

This ports the projection to v2 and wires it into the request path:

- `packages/core/src/session/memory-context.ts` — `SessionMemoryContext.project()`
  replaces the bulk output of an eligible tool result (shell, read, webfetch,
  websearch) with a compact marker that names the call id, the kind, the
  command/url/path, the PII categories found, a redacted preview, and the
  recovery path.
- `packages/core/src/session/evidence.ts` — classifies where the original text
  actually lives (the session history, or the managed tool-output file that
  `ToolOutput` writes) and strips the truncation marker line from the preview.
- `packages/core/src/session/runner/llm.ts` — the projection runs where the
  provider-visible transcript is built (`SessionModelRequest.baseTranscript`),
  so the stored history keeps the original output and only the model view is
  compressed.

Every marker carries a working recovery path: `retrieve=get_tool_call_details(call_id="...")`,
the tool ported to v2 in #205. The projection never removes the original — the
session history in SQLite keeps it, and the managed copy of a bounded output
keeps the full text.

Properties the port keeps:

- **Append-only prefix.** The marker is a pure function of the stored output,
  so the projected prefix of the history does not change when the history
  grows: the provider's cached prefix is not invalidated by the projection.
  (The ledger that will floor the prefix at the provider's cache mark is
  Step 3 of #202.)
- **PII.** The preview is redacted with `PII.redact`, and the marker states
  only the categories found (`pii=api_key`). No secret reaches the marker.
- **Non-text parts survive.** A tool result that carries a file part (an image
  read, a PDF) keeps that part next to the marker; the marker cannot stand in
  for it, and the retrieval tool returns text only.
- **Off by default.** The projection is behind a new v2-line flag
  (`OPENCODE_V2_MEMORY_CONTEXT`, plus `OPENCODE_V2_MEMORY_MIN_CHARS` and
  `OPENCODE_V2_MEMORY_TOOLS`). The v1 `OPENCODE_MEMORY_*` flags do not exist
  on this line and are not read. Step 5 of #202 will route the policy through
  the ledger instead of a flag.

Nothing else changes: the system prompt, the permissions, the user
instructions and the stored session history are untouched.

### How did you verify your code works?

- `bun test test/memory-context.test.ts` — 10 pass, 0 fail (marker content,
  original history untouched, threshold, skipped tools, missing call id,
  prefix stability, PII redaction, file part kept).
- `bun run typecheck` in `packages/core` — clean.
- Root `bun run check` — 35/35 tasks successful (pre-push gate).
- Full `bun test` in `packages/core` — 6713 pass, 43 skip, 8 fail. The 8
  failures are pre-existing and environmental: the same 7 fail on `origin/main`
  (`preload`, shell `case`/process-substitution parsing, `.hg` watcher
  timing) and the 8th is a watcher timing flake.
- **Live A/B on a fork build** (`0.0.0-fork-at-56e1bd694d`, model
  `ladder/standard`, same prompt, same fixture, two separate sessions):
  - the projection really runs — `OPENCODE_V2_MEMORY_CONTEXT_DEBUG=1` writes
    `[mem-context] session=… compacted=1` to the server log, and the baseline
    arm (flag off) writes nothing;
  - the recovery path works — in the variant arm the model had to call
    `get_tool_call_details` (tool calls: `get_tool_call_details` 1, `grep` 2,
    `read` 1, `shell` 3) because it no longer saw the output, and the needle
    (`big-output-line-2999`) still reached the final answer, exactly as in the
    baseline arm (5 turns, `grep` 1, `read` 1, `shell` 1);
  - measured cost, shell fixture (3000-line file): the variant spent 22338
    provider-visible tokens (input + cache read) at the last turn against
    21365 in the baseline — the projection saved ~1.5 KB in the prefix but the
    retrieval round trip cost more. With a 2 KiB threshold the eager
    compaction does not pay for itself in this case.
  - measured cost, read fixture (60 KB file read through the read tool): the
    turn right after the read carried **31695 provider-visible tokens in the
    baseline against 16209 in the variant (-49 %)**, and the cumulative
    provider-visible tokens of the session were 109325 against 95963 (-12 %)
    even though the variant needed two extra turns (it had to retrieve the
    original through `get_tool_call_details`). The projection trace shows
    `compacted=1`/`compacted=2` for that session.

  So the compression pays off exactly when the tool output is much larger
  than the retrieval chunk (`get_tool_call_details` returns 4000 chars by
  default) — Step 5 of #202 has to pick the threshold accordingly.
